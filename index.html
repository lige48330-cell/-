CASE 01 · ERP / 低代码业务系统

公司项目 · 脱敏可核对我的范围：业务流程、对象与字段、页面 / 流程配置、关键单据核验

养殖渔业 ERP：把业务口径收敛成可配置规则

面对基础资料、采购、库存、销售、养殖和设备流程，我先区分业务主体、事件流水与状态结果，再把规则落实到模块、字段、表单、状态和单据路径。

业务风险

业务口径分散，流程、字段、状态和单据之间缺少统一的核验路径。

我推动的动作

梳理角色与流程，抽象对象、字段和状态，配置页面与流程，并按关键单据路径组织核验。

关键判断

先用流程图、功能结构表和页面原型对齐角色、字段与状态，再配置 UI；将主数据、事件流水和状态 / 报表分层，避免功能堆砌。

协作边界

以对象 / 字段 / 状态表和关键单据路径对齐业务与实施；ERP 底座、生产数据环境与运维由团队提供。

可交接结果

形成业务与实施可共同配置、检查和继续维护的对象、字段、状态与关键单据核验口径。

核对方式

脱敏界面、流程 / 原型映射与职责说明；源码、客户数据和生产配置不公开。

  • 需求分析
  • 领域建模
  • 墨刀 / Axure
  • 低代码配置
  • 验收路径

CASE 02 · IOT / ESP32 / 小程序

公司项目 · 脱敏可核对我的范围：管理指标、信息结构、双端界面、状态呈现与云端接口协作

消毒除臭设备管理：把设备反馈组织成运营判断

大屏与小程序面向同一设备管理场景；我负责把团队提供的状态与事件，组织成在线、运行、日志、预警与反馈等可读的管理信息。

业务风险

管理人员需要判断设备是否在线、何时运行、是否异常，以及反馈是否到达管理端。

我推动的动作

定义监控指标与信息结构，把状态、事件、日志和预警映射到双端界面，并参与云端接口字段与状态对齐。

方案判断

方案阶段比较外接 RS485 + 4G DTU 与一体化板，按周期、成本、运维和迁移风险做取舍；该文档是决策参考，不等同于当前固件已实现。

跨端协作

以设备标识、在线 / 运行 / 换水状态和控制回执对齐三端；后端处理、消息协议与 ESP32 固件由团队成员负责。

可交接结果

形成面向运营判断的双端管理视图与状态口径；本页不宣称实体设备与正式现场验收已由个人完成。

核对方式

脱敏大屏与小程序界面、职责与接口协作说明；截图不单独证明固件或服务端由我实现。

  • 状态 / 事件模型
  • uni-app
  • HTTP / MQTT 协作
  • 管理端信息架构
  • ESP32 协作边界

CASE 03 · TAURI / RUST / REACT

私有分支 · 验证记录我的范围：私有化边界、Codex 配置、Provider 运行态与回归验证

Cockpit Tools：跨 React / Tauri / Rust 收敛运行态故障

配置保存成功不等于运行态正确。我从 React 配置入口追到 Tauri 异步命令、Rust 生命周期协调器与 Go sidecar，处理账号配置和本地 gateway 状态不同步。

工程风险

Responses / Chat Completions 切换后，可能出现 gateway 未启动、旧运行态残留或 API Key 账号变化后旧 runtime 未清理。

我推动的动作

沿保存链路追踪到 Rust runtime，定位切换与账号变化后的残留状态，修改生命周期协调并补充聚焦检查。

关键判断

先停止 profile 下旧 runtime，再按当前账号需求协调新 gateway；沿用既有生命周期模块，不增加新依赖。

协作边界

基于既有桌面工具做二次开发，不宣称从零构建整套 AI IDE；私有分支源码不公开。

可交接结果

完成生命周期改动，并把故障路径收敛为可检查的配置、运行态与已知限制说明。

核对方式

TypeScript typecheck、API Key scope 回归、静态断言和 diff 检查通过；目标 Rust 回归因本机缺少工具链未执行。

  • React 19
  • TypeScript
  • Tauri 2 / Rust
  • Go Sidecar
  • Lifecycle

03 / AGENT ENGINEERING

把 Agent 变成可观察、可审查、可接管的交付协作者

我用状态可见、证据可追踪、工具边界和人工接管组织 Agent 工作流，而不是停在提示词；公开工程证明工作流与上下文工程，交互部分明确作为设计约束呈现。

INTERACTION DESIGN CONTRACT

Agent 交互不是聊天框，而是状态、证据与接管设计。

  1. 01
    任务状态可见

    目标、范围、当前步骤和完成条件不藏在聊天记录里。

  2. 02
    上下文与证据可见

    引用资料、事实边界、假设和待确认项明确展示。

  3. 03
    变更影响可确认

    调用工具前说明对象、影响和人工确认点。

  4. 04
    失败可解释、任务可接管

    保留差异、日志、阻塞原因与下一步，让人或下一个 Agent 继续。

ENGINEERING CONTRACT

Agent 工程不是提示词，而是上下文、路由与质量闸门。

  • Context contract项目背景、边界、证据与输出格式结构化。
  • Skill / tool routing能力入口、工具语义、权限与人工接管点可发现。
  • Multi-agent coordination按任务边界并行评审，由主线程整合、验证和负责。
  • Diff / test / handoff结论回到代码差异、测试、日志和交接记录。
输入与边界→Agent 行动→人工判断→验证交接

具体证据，而非方法口号 · Cockpit Tools 展示跨栈运行态改造；Stable-First 与 Code Control Stack 提供工作流、上下文契约、工具路由和质量闸门源码。交互契约属于设计规范，不冒充已上线 Agent 产品。
