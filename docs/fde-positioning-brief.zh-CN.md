# FDE 求职交付 brief

## 目标

把作品集、简历和 GitHub 入口统一成招聘可读的定位：

> FDE / Forward Deployed Engineer：进入业务现场，跨栈推进系统交付，让结果交得出、验得清、团队接得住。

## 招聘方应在 10 秒内读懂

- 我解决业务流程、设备状态和跨核运行态之间的交付风险。
- 我负责从需求收敛、方案与原型，到系统集成、联调验证和团队交接的最后一公里。
- ERP、IoT / ESP32、Cockpit Tools 与 China Job Channels 提供四类分级证据。

## 唯一交付生命周期

现场 → 方案 → 原型 → 集成 → 联调 → 验收 → 交接

领域建模、Agent 协作与团队协调是阶段内的方法，不再作为另一套交付链。

## 首页信息架构

1. 首屏：身份、最终责任和四项证据入口。
2. 三个旗舰案例：问题、职责、关键决策、团队边界、交付结果、验证证据。
3. FDE 责任矩阵：能解决的问题 → 留下的交付物 → 证据入口。
4. Agent 工程增益层：交互契约与工程契约。
5. 补充工程证据：只展示与岗位相关的公开工程，不与主经历同权。

## 三个旗舰案例

1. 养殖渔业 ERP：业务建模、模块 / 字段 / 状态、低代码配置与关键单据核验。
2. 消毒除臭设备联动：监管大屏 + 管理小程序 + 云端接口 + ESP32 状态反馈的管理端协作边界；方案文档可展示技术路径取舍，但不作为已实现硬件证明。
3. Cockpit Tools：Tauri + React + Rust 私有分支、Provider gateway 生命周期和回归验证。

4. China Job Channels：Node Dashboard、Python 采集与离线解析、JSONL 契约、状态真源、失败恢复、57 项 Python 测试和 8 个 JavaScript 检查脚本；原始登录态工程不公开，只展示脱敏结构与验证证据。

## 案例最低证据

每个案例必须回答：

- 现场或工程问题是什么。
- 我实际负责什么。
- 我做了什么关键决策。
- 团队提供什么、哪些不是我独立完成。
- 交付后形成了什么可核对结果。
- 公开证据是什么，哪些材料不能公开。

没有真实量化记录时，使用可核验的前后状态，不编造提升比例。

## 证据与脱敏边界

- 公司 ERP、ESP32 固件、小程序源码、生产配置、客户信息和真实业务数据不公开。
- 公司界面统一标注“真实项目界面 · AI 辅助脱敏”；客户、标识和业务数据已移除。
- 消毒除臭案例只归因管理端、状态呈现与云端接口协作；固件、协议和正式实体设备验收属于团队或待核对边界。
- 架构图和方法图明确标注“示意图 · 非运行截图”。
- 个人公开工程提供可点击源码入口。
- Rust 回归测试未在缺少 `cargo` / `rustc` 的本机环境执行时，必须明确标注为未验证。

## 不再使用的主叙事

- AI 辅助全栈工程师。
- 只按技术栈罗列项目。
- 多套重复的“能力链 / 技术链 / 工作流”。
- 将 IoT 大屏与同一设备小程序拆成两个独立旗舰项目。
- 夸张的“主导、Owner、全链路、已上线”或虚构量化结果。

## 当前验收标准

- 桌面首屏在一个 1440 × 900 视口内完成身份、主张、三项证据和 CTA。
- 390 × 844 手机首屏包含职位、主张、至少一项证据和主案例入口。
- 三个公司 / 私有旗舰案例在能力方法之前出现；个人数据运营工程在公开项目矩阵中直接可见。
- 页面只保留一套七阶段交付生命周期。
- Agent 是工程增益层，不盖过 FDE 主身份。
- 补充项目只提供岗位相关证据，并链接到公开源码。
- 所有可见正文满足可读对比度，无横向溢出和破图。
